chs-compliancepolicygenerator

The Sail Loft. A command line generator that renders a platform specific hardening script from a YAML configuration file through a Jinja2 template. The loft cuts and sews the working sail from the pattern laid under the canvas, and the pattern is the customer's own: no template and no compliance policy ships with the tool.

The repository main.py
ArgumentsAll four are required: compliance standard, config file, output file, and platform
TemplateRead from templates/<platform>/<standard>.j2 relative to the working directory, a tree the caller supplies
GateThe configuration must define a non empty policies list, or the run fails with exit 1
DependenciesJinja2 3.1.2 or later and PyYAML 6.0 or later

Usage

python3 main.py --compliance-standard CIS --config-file config.yaml --output-file hardening.sh --platform linux
OptionWhat it does
-c, --compliance-standardThe compliance standard, for example CIS. Required. It is a path segment in the template lookup, nothing more.
-f, --config-fileThe path to the YAML configuration file. Required.
-o, --output-fileThe path to the output script file. Required.
-p, --platformThe target platform, for example linux or windows. Required. Also a path segment in the template lookup.
-hShow help message and exit.

Stated limits

  • No compliance policy is predefined anywhere in the tool: no CIS or any other standard's content ships with it, and no template ships either, so the repository description's predefined compliance policies do not exist to be chosen. The standard and platform are only path segments.
  • Configuration values land in the output exactly as written and unsanitised, because the output is a script and the template decides where values go. The configuration file is trusted input, and a value carrying shell syntax is carried straight into the generated script.
  • Jinja2's default handling of an undefined name renders blank rather than failing, so a policy key the template spells slightly differently from the configuration writes a blank into the script at that spot while the run still reports success. The generated script needs reading, not just generating.
  • A configuration without a non empty policies list fails the run with exit 1 instead of producing an empty script that reports success. The README also records that a live run was not completed in its documenting environment because the jinja2 package was not installed there.
